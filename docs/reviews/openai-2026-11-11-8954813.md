major, lib/redmine_more_previews/patches/repositories_controller_patch.rb:101-130, entry_converter_for_preview falls back to extension when content sniffing fails, causing wrong CSP and charset decisions
- Problem: entry_converter_for_preview intends to choose the converter “by its content,” but it calls Converter.responsible(path) without disabling the extension fallback. If @repository.cat(@path, @rev) returns nil/empty (SCM glitch, permission, or large file edge), Marcel returns nil and Converter.responsible will pick by file extension. That can incorrectly classify a non-ZIP entry named *.zip as Zippy, enabling allow-top-navigation-by-user-activation in the CSP and adding a UTF-8 charset indiscriminately.
- Scenario: A repository entry “report.zip” actually contains HTML or is unreadable by cat (nil). entry_converter_for_preview writes 0 bytes, Converter.responsible falls back to the “zip” extension, returns “zippy”, and send_more_preview sets sandbox_preview(..., top_navigation: true) and adds charset, relaxing CSP for a non-Zippy preview. The actual conversion may 404, but the CSP relaxation is still wrong.
- Fix: Detect strictly by content only. Avoid using Converter.responsible here (it falls back to extension). Instead, invoke Marcel::MimeType.for on the temp file, and map that mime to an active converter without extension fallback:
  - mime = Marcel::MimeType.for(Pathname.new(path))
  - conv = RedmineMorePreviews::Converter.select_active.values.find {|opts| opts["mime"] == mime}
  - Return conv && conv["converter"], else nil.
  Also guard against nil from @repository.cat: if cat is nil, return nil immediately to avoid any fallback.
Resolution: not changed. The decision deliberately uses the same Converter.responsible as the conversion (content first, then the extension): the CSP and charset belong to the response that converter produces. When content detection gives nothing and the extension says zip, the conversion itself runs Zippy, which fails on non-archive bytes (404), so no foreign html is served under the relaxed CSP; a text/html entry is detected as such and goes to Pass (round 10 test test_html_named_like_an_archive_gets_no_top_navigation). Content-only detection would make the header disagree with the converter that actually renders.

minor, lib/redmine_more_previews/redmine_more_previews.rb:121-152, possible reader thread leak on imagemagick_list_formats timeout
- Problem: When the “convert -list format” subprocess exceeds the timeout, the code kills the process and returns nil but never joins the reader thread (Thread.new { out.read }). This leaves a stray thread that can accumulate if timeouts happen (e.g., transient convert issues), slowly leaking resources.
- Scenario: On a host with a hung ImageMagick binary, each settings page render calls unreadable_maggie_formats and thus imagemagick_formats. If the list call keeps timing out, the code spawns reader threads that are not joined, leading to a growing number of Ruby threads and eventual memory/FD pressure.
- Fix: After killing the process on timeout, also close the IO and join the reader thread before returning:
  - out.close rescue nil
  - reader.join rescue nil
  Alternatively, read from out with nonblocking IO in the main thread and avoid the extra thread.
Resolution: not changed (upstream code, aa28b8b). On timeout the whole process group is killed and waited for; the pipe then reaches EOF and the reader thread ends; a successful result is cached once per process, a failure is asked again only on the next settings render or conversion.

minor, lib/redmine_more_previews/patches/controller_helper.rb:82-95, preview_content_type also uses Converter.responsible with extension fallback, which can mislabel charset for non-plugin HTML
- Problem: preview_content_type uses plugin_html_preview?(source, options), which internally calls Converter.responsible(source, options). With options = {} (attachments), a failure to detect by content lets Converter.responsible fall back to extension. That can erroneously add “; charset=utf-8” to a non-plugin HTML preview (or miss it when needed).
- Scenario: An attachment foo.zip that actually contains HTML, but Marcel returns nil (corrupt file start). Converter.responsible chooses Zippy by extension, plugin_html_preview? returns true, and preview_content_type appends charset even though the content is not Zippy-generated HTML that lacks <meta charset>. Conversely, a Cliff HTML that fails content detection might miss the charset header.
- Fix: For the charset decision, detect strictly by content. Use Marcel::MimeType.for on the file and map to converters that write HTML (cliff, zippy) without allowing extension fallback. Or pass a flag to a new responsible_by_content_only helper that does not fall back to extension.
Resolution: not changed, same reason as the major finding above: the charset follows the converter the conversion chooses; for an attachment whose start Marcel cannot type, the conversion falls back to the extension too, and Zippy and Cliff both write UTF-8.
