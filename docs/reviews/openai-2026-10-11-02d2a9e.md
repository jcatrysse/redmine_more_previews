## Part 1 of 1

- Severity: major
  File: converters/maggie/lib/maggie.rb:43-58 (application/pdf branch)
  Problem: When Ghostscript is unavailable (Redmine::Thumbnail.gs_available? returns false), the code copies the original PDF to a file named with the requested image extension (out.<preview_format>), which is then moved to index.<preview_format>. This serves PDF bytes under an image filename/extension, likely with an image content type, producing broken previews and misleading MIME types.
  Failure scenario: On a server without Ghostscript, with Maggie configured for pdf -> png, requesting /attachments/more_preview/:id/index.png returns a file starting with “%PDF” but served as image/png. Browsers will fail to display the preview, and some clients may mis-handle caching or security checks because of the mismatched type.
  Fix: Do not copy the PDF when Ghostscript is unavailable. Instead, return nil so the caller treats the file as “no preview available” (consistent with other unsupported types), or explicitly produce a PDF preview (set preview_format to pdf and name/output ‘out.pdf’) and ensure the controller sends the correct content type. The simplest safe change here is to replace the else branch with nil.

- Severity: major
  File: converters/maggie/lib/maggie.rb:33-40, 60-63 (LIMITS and convert_command)
  Problem: The hard-coded -limit resources include width and height (e.g., -limit width 16KP, -limit height 16KP). These are not supported by all ImageMagick versions (notably many ImageMagick 6.x builds). Passing unknown resource types causes convert to exit with an error, breaking all Maggie conversions.
  Failure scenario: On a host with ImageMagick 6.9.x (common on LTS distros), the constructed command includes “-limit width … -limit height …”; convert prints “unrecognized resource type `width`” and exits non‑zero. The preview endpoint then returns an error or no preview for otherwise valid PNG/JPEG/PDF files.
  Fix: Only pass -limit options that are guaranteed across supported ImageMagick versions (area, memory, map, disk are widely supported). Feature-detect supported resources at boot (e.g., run convert/magick -list resource and intersect with the desired set), or drop width/height entirely. Example: keep area, memory, map, disk; conditionally include width/height only if listed by -list resource. Add a unit test that tolerates absent width/height on older IM versions by asserting at least the core limits are present.

## Resolutions

1. major, PDF copied as `out.<format>` when Ghostscript is missing: **not changed, pre-existing and
   outside this decision.** The branch was there before (upstream keeps it as well); since `5f38162`
   only a file that passes `Redmine::Thumbnail.valid_pdf_magic?` reaches it, and the response is
   sandboxed and sent with `nosniff`, so the browser shows a broken image, nothing runs. GEOxyz
   installs Ghostscript (required under "After the upgrade"), and after
   `rake redmine_more_previews:use_core_previews` Maggie is off. Noted in the plan as a known
   limitation.
2. major, `-limit width/height` unknown to older ImageMagick 6: **not a defect for the supported
   servers.** Width and height limits exist since ImageMagick 6.8; Ubuntu 24.04 ships 6.9.12-98,
   which lists them (`convert -list resource`) and accepts the exact command
   (`convert -limit width 16KP -limit height 16KP -limit area 128MP ...` exits 0).
   `test_maggie_still_converts_a_png_and_a_pdf` runs the real conversions with these limits.
